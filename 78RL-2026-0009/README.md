## At a glance

The checked-in [345-byte JXL file](input/poc.jxl) has an 8×8 cropped frame on a 32,768×10,923 canvas. With `--disable_output`, `djxl` still decodes to floating-point pixels. A three-channel, four-byte-per-channel packed canvas requires 4,295,098,368 bytes: **2³² + 131,072**. On a 32-bit build, the old `pixels_size` calculation wraps to 131,072 before allocation.

The ordinary 0.11.1 `djxl` process exits on SIGSEGV. Valgrind records invalid 4-byte writes in the output callback before that crash. The same input is rejected at frame creation by 0.11.2. A [256×256 control](input/control.jxl) generated by the same encoder decodes on both releases.

## Root cause

In 0.11.1, `PackedImage::Create()` calculates the row stride and allocates the product of stride and canvas height without checking for `size_t` overflow. The decoder then copies pixel rows into that undersized packed-image buffer. The input is only hundreds of bytes because its actual frame is 8×8; the large dimensions are in the canvas header.

The vulnerable path is reached by the real `djxl` command line. `--disable_output` avoids writing a very large file, but it does not skip pixel decoding or packed-image creation. The pre-fix [Valgrind transcript](output/memcheck-0.11.1.txt) identifies the invalid `memcpy` write at `lib/extras/dec/jxl.cc:506`.

### The fix

[Upstream PR #4589](https://github.com/libjxl/libjxl/pull/4589), included in the [0.11.2 release](https://github.com/libjxl/libjxl/releases/tag/v0.11.2), adds a `VerifyDimensions()` call before allocation. Its checks cover the row-byte multiplication, aligned stride, and total pixel-buffer multiplication. The relevant new entry and total-size check are:

```cpp
JXL_RETURN_IF_ERROR(VerifyDimensions(xsize, ysize, format));
PackedImage image(xsize, ysize, format, CalcStride(format, xsize));
```

Inside the new `VerifyDimensions()` helper, the total-size check is:

```cpp
size_t pixels_size = ysize * stride;
if ((pixels_size / stride) != ysize) {
  return JXL_FAILURE("Image too big");
}
```

For the checked-in file, 0.11.2 reports `Failed to create image frame` instead of decoding into the wrapped allocation. The patch is explicitly named in upstream release notes; this case does not present it as an undisclosed fix.

## How the proof of concept works

[`make-poc.cc`](make-poc.cc) calls only exported `JxlEncoder*` APIs. It encodes the same 8×8 RGB pixels twice: once with the oversized 32,768×10,923 canvas ([trigger](input/poc.jxl)), and once with a 256×256 canvas ([control](input/control.jxl)). Both are checked-in byte payloads. Every runner regenerates its input inside Docker and compares it byte-for-byte with the checked-in file before invoking `djxl`.

[`run-original.sh`](run-original.sh) compares the trigger on 0.11.1 and 0.11.2. [`run-control.sh`](run-control.sh) checks the small canvas on both. [`run-memcheck.sh`](run-memcheck.sh) repeats the vulnerable CLI under Valgrind to classify the write. [`run.sh`](run.sh) builds the pinned versions and invokes all three scripts.

## Results

### libjxl 0.11.1: oversized canvas

The [ordinary CLI log](output/original-0.11.1.txt) records the 0.11.1 decoder banner, a regenerated-payload match, and exit 139 after the decoder crashes. The [Valgrind log](output/memcheck-0.11.1.txt) records `Invalid write of size 4` at `jxl.cc:506` in the image-output callback, followed by SIGSEGV. Both runners assert those results.

### libjxl 0.11.2: oversized canvas

The [fixed CLI log](output/original-0.11.2.txt) records `Failed to create image frame` and exit 1 for the same payload. No successful pixel decode is claimed for this input.

### Small-canvas control

The [0.11.1](output/control-0.11.1.txt) and [0.11.2](output/control-0.11.2.txt) control logs both record `Decoded to pixels` and exit 0. This separates oversized allocation arithmetic from a general failure to decode the generated image format.

## Impact and limitations

The demonstrated effect is an invalid write and crash in the native 32-bit `djxl` CLI when it processes the checked-in JXL file. The Valgrind result establishes memory corruption on that path; the ordinary build crash alone would establish only process termination. This case does not demonstrate code execution, a network entry point, or reachability in a specific downstream application. A 64-bit build and other libjxl releases were not tested here.

This case tests the original trigger and a small control. It does not assert a post-fix bypass or prove that every possible input and later version is safe.
