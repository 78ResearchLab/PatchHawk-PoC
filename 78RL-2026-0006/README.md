# 78RL-2026-0006

## OpenImageIO: a DDS header-controlled copy writes past a four-byte stack variable

| | |
|---|---|
| **Affected** | OpenImageIO 3.1.15.0 |
| **Fixed in** | OpenImageIO 3.1.16.0 |
| **Advisory** | No matching CVE or dedicated advisory was found as of 2026-09-29. `78RL-2026-0006` is a project-assigned identifier so this reproducer can be cited |
| **Severity** | Not assigned by upstream |
| **Class** | CWE-121 / CWE-787 stack out-of-bounds **write** |
| **Where** | `src/dds.imageio/ddsinput.cpp`, `DDSInput::internal_readimg()` |
| **Entry point** | `ImageInput::open()` followed by `ImageInput::read_image()` on a DDS file |

## At a glance

OpenImageIO's DDS reader derives its native bytes-per-pixel value, `m_Bpp`, from
the file's `RGBBitCount` field. In 3.1.15.0, one uncompressed decoding path uses
that value as the length of a `memcpy` into a four-byte `uint32_t` local variable.

The 136-byte proof of concept declares 64 bits per pixel, making `m_Bpp` equal
to 8. The decoder therefore copies eight file bytes into a four-byte stack
object. AddressSanitizer reports a `WRITE of size 8` and terminates the vulnerable
process with status 99. The same public API call reads the file successfully on
3.1.16.0, where the copy is clamped to the destination size.

This is a deterministic sanitizer finding. A crash in an ordinary, unsanitized
build and code execution are not demonstrated here.

## Root cause

In OpenImageIO 3.1.15.0, `m_Bpp` is computed from a field in the DDS header:

```cpp
m_Bpp = (m_dds.fmt.bpp + 7) >> 3;
```

The mask-based uncompressed decoder later copies one native pixel into a local
`uint32_t` (`ddsinput.cpp:994-995` in the vulnerable release):

```cpp
uint32_t pixel = 0;
memcpy(&pixel, tmp.get() + x * m_Bpp, m_Bpp);
```

The destination is always four bytes, while the file controls the copy length
through `m_Bpp`. Any accepted value above four writes beyond `pixel`; the bytes
written also come directly from the file.

### The fix

OpenImageIO 3.1.16.0 clamps the copy to the size of the destination:

```diff
 uint32_t pixel = 0;
-memcpy(&pixel, tmp.get() + x * m_Bpp, m_Bpp);
+memcpy(&pixel, tmp.get() + x * m_Bpp,
+       std::min(m_Bpp, (int)sizeof(pixel)));
```

The release also rejects uncompressed native pixel sizes outside the range of
1 to 16 bytes. This PoC deliberately uses eight bytes, which remains inside
that range. The differential result therefore exercises the copy clamp itself,
rather than being stopped by the new header sanity check.

See the [fix commit](https://github.com/AcademySoftwareFoundation/OpenImageIO/commit/d11941e)
and [3.1.16.0 release notes](https://github.com/AcademySoftwareFoundation/OpenImageIO/releases/tag/v3.1.16.0)
for the upstream change.

## How the proof of concept works

[`poc.dds`](poc.dds) is a 136-byte file generated by
[`make-poc.py`](make-poc.py). Its SHA-256 is
`983e3b874b94e5df45907def4a3666530c4fc63cc05bed5cba8769a85539d89a`.

The relevant fields are:

| Field | Value | Effect |
|---|---:|---|
| Width × height | 1 × 1 | Keeps the file and allocation minimal |
| Pixel-format flags | `DDS_PF_ALPHA` (`0x1`) | Reaches the accepted mask-based path |
| `RGBBitCount` | 64 | Produces `m_Bpp = 8` |
| Pixel data | `41 41 41 41 de ad be ef` | Supplies all eight bytes copied from the file |

An older bit-depth whitelist checks only formats marked with `DDS_PF_RGB`,
`DDS_PF_LUMINANCE`, `DDS_PF_YUV`, or `DDS_PF_ALPHAONLY`. A format marked only
with `DDS_PF_ALPHA` passes an earlier data-presence check but does not enter that
whitelist. It produces four output channels while `m_Bpp` is eight, so the
decoder takes the per-pixel mask path containing the vulnerable copy.

The checked-in binary is reproducible:

```bash
python3 make-poc.py /tmp/rebuilt.dds
cmp poc.dds /tmp/rebuilt.dds
```

## How to reproduce

Everything runs in Docker; no OpenImageIO files are installed on the host.

```bash
docker build -t openimageio-poc:0006 build/
./run.sh
```

The image builds OpenImageIO 3.1.15.0 and 3.1.16.0 from their release archives
with identical AddressSanitizer flags, then compiles the same minimal public-API
reader against each build. The Dockerfile verifies these source hashes before
building:

[`build/oiio_read.cpp`](build/oiio_read.cpp) uses only the documented

returned `ImageSpec`, and requests the file's native pixel format with
`read_image()`.

## Impact and limitations

This path writes file-supplied bytes beyond a stack variable while decoding an
image. The trigger reaches OpenImageIO through its ordinary public image-reading
API, so applications that decode untrusted DDS content can reach the affected
code without calling plugin internals.

The PoC proves the out-of-bounds write under AddressSanitizer and verifies the
fixed behavior on the next release. It does not demonstrate an unsanitized
crash, control-flow corruption, or code execution. The overwrite shown here is
four bytes past `pixel`; compiler layout and hardening determine what follows
that object in a production build.

This issue should not be confused with CVE-2026-7582, an older OpenImageIO DDS
out-of-bounds write fixed by a different change, PR #5131. The code, trigger,
and upstream fix documented here are from PR #5287.
